# Research: network-security, NDR and observability vendors

Date: 2026-11-23. Companion to [`RESEARCH-wave1.md`](RESEARCH-wave1.md), which covered the eBPF and Kubernetes tools (Hubble, Tetragon, Retina, Falco and others) and is not repeated here. This round covers the commercial network-security, DDoS, NDR and flow-analytics field plus the open network-monitoring tools.

## How to read the evidence marks

- **[V]** The claim was read from a page fetched in this session.
- **[U]** Not verified from a fetched page. Most of this document is [U]: the first fetch attempts at several vendor product pages returned 404 or a landing page, so the rest came from web-search result summaries of vendor pages (title and snippet, not the page body) and from general knowledge. Treat [U] as a lead to check, not a fact. A source URL on a [U] row is the page the search surfaced, not a page read in full.
- Vendor performance and accuracy claims (mitigation seconds, false-positive reductions, "30% more attacks") are marketing. They are quoted only to show what the vendor emphasises and are never relied on.
- No proprietary content is copied. Everything below is a paraphrase of a capability.

Pages fetched and read in full: Palo Alto Networks DNS Security landing page, Cloudflare DDoS landing page, FoxIO JA4 technical spec, IANA IPFIX information element registry.

## Patterns across the field

1. **Per-vector, baseline-relative flood detection with an absolute floor.** F5, Fortinet, Check Point, Kentik and Cloudflare all separate flood vectors (SYN, UDP, ICMP, fragments), learn or compute a baseline and let the operator tune sensitivity. FortiDDoS adds a detect-only mode first. [U]
2. **Top-N sources at attack time and a response that is a deny of the offending source.** Check Point and F5 name bad actors; Kentik and Cloudflare turn an alert into a mitigation (RTBH, Flowspec, Magic Transit On Demand). The mitigation is usually automatic or one click. [U]
3. **Encrypted-traffic hygiene as an inventory.** ExtraHop, Zeek, ntopng and Cisco all list weak or deprecated TLS and expiring certificates. Everything that needs the certificate or ServerHello gets thin under TLS 1.3 unless decrypted. [U]
4. **DNS behavioural analytics** (tunneling, DGA, failure storms) is near-universal: Palo Alto [V], Elastic, ntopng, Cortex. [U except Palo Alto]
5. **Flow export in standard fields** (IPFIX, NetFlow v9) is the lingua franca between collectors and analytics. Kentik, Cloudflare, Cisco, Gigamon and nProbe all speak it. [U]
6. **Prioritisation and entity context** (Vectra urgency, Darktrace, Arista entity graph) is the NDR differentiator. [U]
7. **Safety rails before enforcement**: FortiDDoS Detection Mode, Cisco policy simulation, host-group policy tests. Netra already has the strongest version of this idea (deny preview, counterfactual preview, self-lockout check, lease that fails open).
8. **Capacity forecasting** (a conntrack table or port range filling) is not a headline feature of any product above; capacity alerts exist, forecasts to exhaustion are an operations feature of monitoring tools. [U]

## What Netra already had (read from code and docs)

- **Floods and scans:** per-workload egress port-scan, fan-out, lateral and SYN-flood findings (`internal/scandetect`); optional volumetric auto-mitigation of UDP destinations and SYN floods (`internal/automitigate`); the XDP shield's per-class (syn, udp, icmp, other) counters and per-source SYN attempt and denied counters (`internal/shielddiag`), with a fixed cumulative threshold; per-second kernel counters in the metrics platform (`ipv4.udppackets`, `ip.tcp_syn_queue`, `ip.tcpsyncookies`, `ipv4.icmp`) with anomaly detection.
- **DNS:** tunneling, DGA, beaconing and NXDOMAIN/SERVFAIL storms (`internal/dnsdetect`), DNS board, DNS intel and encrypted-DNS findings. A DNS analytics feature would have duplicated this.
- **TLS:** JA3 and JA4 fingerprints with a rare-fingerprint risk board (`internal/tlsfp`), ECH blindness (`internal/echblind`), SNI metadata, TLS-to-cleartext downgrade correlation. No TLS version inventory, and no certificate or cipher-suite data is captured.
- **Capacity:** conntrack utilization as a metric with a threshold alert (`conntrack_table_full`) and a point-in-time kernel-diagnostics finding; a linear forecast exists only for the cluster health score (`internal/forecast`). Nothing watched the ephemeral port range.
- **Export:** SIEM export of current destination-flow counters (`/api/v1/export/flows`), syslog, OTLP, Loki, Snowflake and metrics exporters. Flow history (`internal/flowlog`) was queryable as JSON only.
- **Safety:** deny preview (live and historical), self-lockout check, leased enforce that fails open, plan-token flow for policy apply.

## What was missing

1. A learned baseline per flood vector for inbound traffic on a node, and a rate (not a cumulative count) per source.
2. A deny suggestion tied to a flood source that goes through the existing preview and lockout check.
3. Any forecast of the conntrack table or the ephemeral port range filling.
4. A TLS version inventory (what clients can speak), even from metadata alone.
5. Flow history in a standard field vocabulary and a CSV a spreadsheet or analytics tool can load.
6. A declarative file for leased deny rules with a plan and diff before apply.

## Boundaries checked for what was built

- No payload, argv or Secret read. The ephemeral collector reads `/proc/net/{tcp,tcp6,udp,udp6}` and `ip_local_port_range` only, keeps no address in any metric, and writes nothing.
- No MCP or LLM SDK, no new Go dependency, no change to `go.mod`, Dockerfiles, workflows or any `bpf/*.c`.
- New MCP tools are read-only and sit outside `NETRA_MCP_ALLOW_MUTATIONS`; nothing mutating was added.
- A suggested deny is text plus a preview request body. Applying one stays the existing leased enforce, which fails open. No policy apply was touched.
- BPF attachment inventory, netlink recorder and the metrics platform stay read-only; no Cilium-owned map is touched; no PacketWolf sync.
